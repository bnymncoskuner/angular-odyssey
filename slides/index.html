Angular Odyssey

From Modules to Signals

Bunyamin Coskuner
Senior Software Engineer at Dreamix

Welcome everyone. Today we're going on an odyssey through Angular's evolution — from the NgModule era all the way to the fully reactive, signal-based framework we have today. We'll look at the same app built 6 different times, each using the actual Angular version of its era. Our journey starts with a simple boat...
This is our roadmap — 6 islands, each representing an Angular era. We'll sail from island to island, visiting each milestone chronologically. The journey spans from 2017 (Angular 4) to 2026 (Angular 22).
Same features in every app: book search with the mock API, infinite scroll, book detail with related books, favorites persisted in localStorage, profile form with validation, auth guard that redirects to profile if no display name set, lazy loading for all feature routes, and reactive form validation.
Six apps running in parallel — each docked at its own port. All connect to a shared mock API on port 3000. You can run them all simultaneously with start-all.sh. Each uses the actual Angular version of its era with the correct Node version.

NgModule & Class Guard


@NgModule({
  declarations: [AppComponent, SearchComponent],
  imports: [BrowserModule, HttpClientModule, ReactiveFormsModule],
  bootstrap: [AppComponent]
})
export class AppModule {}
          

@Injectable({ providedIn: 'root' })
export class AuthGuard implements CanActivate {
  constructor(private profileService: ProfileService, private router: Router) {}
  canActivate(): boolean | UrlTree {
    return this.profileService.hasDisplayName() 
      ? true : this.router.createUrlTree(['/profile']);
  }
}
The "classic" Angular era. Everything lives in NgModules — every component must be declared, every module imported. Guards are full classes implementing CanActivate. DI is constructor-based. providedIn:'root' (v6+) was the first tree-shaking improvement.

Ivy Begins (v6–v9)


// The biggest internal rewrite since Angular 2:
// v6  (2018) — Ivy announced, under active development
// v8  (2019) — Ivy preview (opt-in flag)
// v9  (2020) — Ivy enabled by default!

// What Ivy brought:
// ✓ 30% smaller bundles for small apps
// ✓ 40-50% faster tests
// ✓ AOT compilation in dev mode by default
// ✓ Better debugging (ng.getComponent() in DevTools)

The new rendering engine — announced in v6, default by v9. But View Engine sticks around until v13...

Ivy was Angular's biggest bet. The old View Engine compiled everything as a single unit — Ivy compiles each component independently. This took 3.5 years to fully roll out. By v9 it's the default, but View Engine isn't removed yet — that happens in the next era (v13).

Strict mode means you get compile-time errors for things that would previously silently fail at runtime — accessing a possibly-null property, using the wrong type in a template binding, or forgetting a required input. It made Angular apps significantly more reliable but required more explicit typing throughout the codebase.

After 8 major releases (v6→v13), the migration is done. View Engine is gone. Ivy's independent compilation model enables standalone components in the next era.

This is where Ivy's journey ends. IE11 support was also dropped in v13, enabling modern JS output. These two cleanups — removing View Engine and IE11 — unlocked everything that follows.

This era was mostly about cleanup and strictness: IE11 dropped, View Engine removed, strict mode by default. Not flashy, but it set the foundation for what came next. Typed forms landed here — notice how controls.email.value is typed as string|null.
Important context: In late 2021, Angular's original tech lead (who had been there since 2010) left after 11.5 years. New leadership took over product and engineering direction. This kicked off what the community calls the "Angular Renaissance" — a bold push toward simplicity, reactivity, and modern DX. The pace of innovation accelerated dramatically from here: v14 (standalone), v16 (signals), v17 (@if/@for, @defer) all landed in rapid succession.

Standalone Components


@Component({
  standalone: true,
  imports: [CommonModule, RouterLink, BookCardComponent],
  template: `...`
})
export class FavoritesComponent {
  favoritesService = inject(FavoritesService);
}

No NgModule needed! Components declare their own imports.

The biggest architectural shift since Angular 2. Standalone means a component is self-contained — declares its own dependencies. No more SharedModule, no more barrel imports. inject() replaces constructor DI — simpler, works in functions, tree-shakable. Over 90% of Angular devs adopted standalone by v19.

Signals Arrive (v16 Developer Preview)


// v16: Signals introduced — the future of Angular state
import { signal, computed, effect } from '@angular/core';

const count = signal(0);
const doubled = computed(() => count() * 2);

effect(() => console.log('Count:', count()));

count.set(5); // logs "Count: 5"
          

// RxJS interop: bridge between signals and observables
import { toSignal, toObservable } from '@angular/core/rxjs-interop';

data = toSignal(this.http.get('/api/data'), { initialValue: [] });

Signals landed in v16 as dev preview. Made Zone.js optional and enabled fine-grained reactivity. Stable in v17+.

Signals were the most anticipated feature since Ivy. Inspired by SolidJS and Preact signals. The Angular RFC got 682 comments! toSignal/toObservable bridge the RxJS world to signals. TC39 is now working on adding signals to JavaScript itself, with Angular's implementation as reference. Effect was kept in dev preview longer because they wanted to get the semantics right.

@if / @for Control Flow


@if (books().length > 0) {
  @for (book of books(); track book.id) {
    <app-book-card [book]="book" />
  }
} @else {
  <p>No results found</p>
}

Replaces *ngIf / *ngFor — track is mandatory, up to 90% faster than *ngFor in benchmarks.

The new block syntax is closer to JavaScript (if/else/for vs *ngIf/*ngFor). Track is mandatory — a pain point with *ngFor where people forgot trackBy and got performance issues. The 90% improvement comes from a new diffing algorithm. @else if is now possible — was impossible with *ngIf. Structural directives were deprecated in v20 and removed in v22.

Signals Replace BehaviorSubject


// v17-v19: Signals for state — no more BehaviorSubject!
readonly books = signal<Book[]>([]);
readonly isLoading = signal(false);
readonly totalItems = signal(0);
readonly hasMore = computed(() => this.books().length < this.totalItems());

search(query: string): void {
  this.isLoading.set(true);
  this.books.set([]);
  this.fetchPage(0);
}

// Template: just call the signal
// {{ books().length }} results
// @if (isLoading()) { <spinner /> }

No subjects, no subscriptions, no async pipe. Signals are synchronous, fine-grained, and composable via computed().

effect() for Side Effects


// v17-v19: Automatic localStorage sync via effect()
@Injectable({ providedIn: 'root' })
export class ProfileService {
  readonly profile = signal<UserProfile | null>(this.loadFromStorage());

  constructor() {
    effect(() => {
      const p = this.profile();
      if (p) localStorage.setItem('profile', JSON.stringify(p));
      else localStorage.removeItem('profile');
    });
  }
}

Signal Inputs, Outputs & model()


// BEFORE: Decorator-based
@Input() book!: Book;
@Output() favorited = new EventEmitter<Book>();

// AFTER: Function-based (v17 preview → v19 stable)
book = input.required<Book>();
favorited = output<Book>();

// model() — two-way binding in one signal (v17.2+)
value = model<string>('');  // replaces @Input + @Output pair
// Parent: <app-slider [(value)]="volume" />

Everything becomes a signal — inputs, outputs, queries, two-way bindings. No more decorators for component communication.

Signal inputs are read-only — data flows one direction. output() replaces EventEmitter. model() is the two-way binding primitive — replaces the @Input() + @Output() + Change suffix pattern. Great for UI components like sliders, toggles, custom form controls. viewChild()/contentChild() also return signals. All went stable in v19.

rxResource() — Async Data


// v19: rxResource wraps Observable with built-in state
bookResource = rxResource<Book | null, string>({
  request: this.id,  // signal passed directly!
  loader: ({ request: id }) => this.svc.getBookById(id),
});
book = computed(() => this.bookResource.value() ?? null);
          

<!-- Built-in loading & error — no manual signals! -->
@if (bookResource.isLoading()) {
  <app-skeleton />
} @else if (bookResource.error()) {
  <p>Something went wrong</p>
} @else if (book()) {
  <h1>{{ book()!.title }}</h1>
}

Introduced in v19. Replaces manual signal + effect + subscribe.

rxResource wraps an Observable-based loader with built-in state management. No more manual isLoading/error signals. The request signal triggers refetch automatically when it changes. Note: in v19 the API uses request+loader. In v20+ it was renamed to params+stream when it stabilized. resource() is the Promise-based equivalent. httpResource() (v20) goes one step further — no service needed, just a URL.

SSR went from painful to production-ready. Non-destructive hydration (v16), @angular/ssr package (v17), incremental hydration (v19). One command to add.

Angular SSR has improved massively. Used to be Angular Universal — quite painful to set up. Now it's one CLI command (ng add @angular/ssr), hydration is automatic, and incremental hydration (v19) means you don't even load all JS upfront. Google reported 45% LCP improvement with hydration. Virgin Media O2 saw 112% increase in sales after adopting Angular SSR.

httpResource() (new in v20)


// httpResource: direct URL — no service needed!
bookResource = httpResource<GoogleBookItem>(
  () => `/api/volumes/${this.id()}`
);

// rxResource stable in v20+: renamed from v19
// v19: request + loader → v20+: params + stream
bookResource = rxResource<Book | null, string>({
  params: this.id,
  stream: ({ params: id }) => this.svc.getBookById(id),
});

httpResource new in v20. rxResource stabilized: request→params, loader→stream

httpResource is like a reactive fetch() — pass a URL as a signal expression, get back value, isLoading, error, headers as signals. Uses HttpClient under the hood so interceptors still work. The API rename from request/loader to params/stream happened when rxResource stabilized — breaking change but they improved naming.

Zoneless Bootstrap


// v20-v21: No zone.js! No provideZoneChangeDetection()!
export const appConfig: ApplicationConfig = {
  providers: [
    provideBrowserGlobalErrorListeners(), // replaces zone error handling
    provideRouter(routes, withComponentInputBinding()),
    provideHttpClient(),
  ]
};

// Zone.js is completely removed from the bundle
// Change detection driven purely by signals
Zone.js monkey-patches all async APIs (setTimeout, Promise, XHR) to know when to run change detection. With signals, Angular knows exactly what changed — no patching needed. provideBrowserGlobalErrorListeners() handles uncaught errors that zone.js used to catch. Hundreds of zoneless apps running in production at Google. Over 1400 public Angular apps on HTTP Archive are already zoneless.

linkedSignal() (stable in v20)


// Mutable state that resets when a dependency changes
const options = signal(['apple', 'banana', 'fig']);

// Resets to first option whenever options change
const choice = linkedSignal(() => options()[0]);

choice.set('fig');       // user picks fig
options.set(['kiwi']);   // options change → choice resets to 'kiwi'

Common UI pattern: selection state that tracks a parent signal but can be locally overridden.

Solves a common UI problem: a dropdown selection that resets when available options change, but can be manually overridden by the user. Without linkedSignal, people used effects to reset state — error-prone and harder to reason about. The advanced form gives access to previous values too.

@Service()


// Replaces @Injectable({ providedIn: 'root' })
import { Service } from '@angular/core';

@Service()
export class BookSearchService {
  private readonly http = inject(HttpClient);
  // ... cleaner, less boilerplate
}

Singleton by default — no providedIn needed.

Syntactic sugar but meaningful — reduces boilerplate and makes intent clearer. @Injectable still exists for constructor injection or non-root providers. @Service is the "90% use case" decorator.

injectAsync()


// Lazy-load a service on demand — separate chunk!
import { injectAsync, onIdle } from '@angular/core';

export class Favorites {
  private loadExport = injectAsync(
    () => import('./export.service'),
    { prefetch: onIdle }
  );

  async export() {
    const svc = await this.loadExport();
    svc.downloadFavorites(this.books());
  }
}

Service code not loaded until called — true code splitting for DI.

Big deal for large apps. Previously, components and routes could be lazy-loaded but services were always eagerly loaded. injectAsync splits the service into its own chunk. In the demo app, the ExportService is 397 bytes in its own chunk — only loaded when the user clicks "Export". prefetch:onIdle pre-downloads it during browser idle time so when the user clicks, it's instant.
